2. Checkout Request Lifecycle

End-to-end Stripe payment with 3D Secure. The webhook, not the redirect, marks the order paid.

sequenceDiagram
    autonumber
    participant C as Client
    participant A as Node.js API
    participant D as Database
    participant G as Gateway (Stripe)
    participant B as Bank (3DS)

    C->>A: POST /orders (cart, Idempotency-Key)
    A->>D: Create order (status: pending)
    A->>G: paymentIntents.create(amount, metadata.orderId)
    G-->>A: client_secret
    A-->>C: client_secret
    C->>G: confirmPayment(card via Elements)
    G->>B: 3D Secure challenge (if needed)
    B-->>G: Approved
    G-->>C: Redirect to return_url
    G->>A: Webhook payment_intent.succeeded
    A->>A: Verify signature, dedupe event.id
    A->>D: Mark order paid (amount + currency checked)
    A-->>G: 200 OK

4. Payment Verification (Webhook)

What the server checks before fulfilling an order. See Payment verification.md.

flowchart TD
    A[Webhook POST received] --> B{Raw body + signature valid?}
    B -- No --> X[Return 400, ignore]
    B -- Yes --> C{event.id already processed?}
    C -- Yes --> Y[Return 200, skip]
    C -- No --> D{Status succeeded / captured?}
    D -- No --> E[Update order: failed / pending]
    D -- Yes --> F{Amount and currency match DB order?}
    F -- No --> G[Mark amount_mismatch, alert team]
    F -- Yes --> H[Mark order paid, only if status = pending]
    H --> I[Save event.id as processed]
    I --> J[Push email / invoice / stock jobs to queue]
    J --> K[Return 200 OK fast]
    E --> K
    G --> K

5. Razorpay Checkout Signature Verification

HMAC-SHA256 of order_id|payment_id with the key secret.

sequenceDiagram
    autonumber
    participant C as Client
    participant A as Node.js API
    participant R as Razorpay
    participant D as Database

    C->>A: POST /orders
    A->>R: orders.create(amount, receipt)
    R-->>A: razorpay_order_id
    A->>D: Save order (pending, razorpay_order_id)
    A-->>C: razorpay_order_id, key_id
    C->>R: Open Razorpay Checkout, user pays
    R-->>C: payment_id, order_id, signature
    C->>A: POST /payments/razorpay/verify
    A->>A: HMAC_SHA256(order_id + "|" + payment_id, key_secret)
    alt signature matches (timingSafeEqual)
        A->>R: payments.fetch(payment_id)
        R-->>A: amount, status captured
        A->>D: Mark paid if amount matches
        A-->>C: 200 OK
    else mismatch
        A-->>C: 400 Invalid signature
    end

6. Idempotency (Client to API)

Redis SET NX lock so double clicks and retries never charge twice. See Idempotency.md.

flowchart TD
    A[POST /orders with Idempotency-Key] --> B{Key present?}
    B -- No --> X[400 Bad Request]
    B -- Yes --> C[Redis SET idem:user:key processing NX EX 86400]
    C --> D{Key was new?}
    D -- Yes --> E[Process request]
    E --> F[Call gateway with idempotencyKey = order id]
    F --> G{Response 5xx?}
    G -- Yes --> H[Delete key so retry can run]
    G -- No --> I[Store status code + body under key]
    D -- No --> J{Stored status?}
    J -- processing --> K[409 Request in progress]
    J -- done --> L[Replay stored response]

7. Webhook Duplicate Delivery

Gateways deliver at least once. A unique index on eventId makes reprocessing a no-op.

sequenceDiagram
    participant G as Gateway
    participant A as Webhook Handler
    participant D as Database

    G->>A: event evt_123 (attempt 1)
    A->>D: insert ProcessedEvent(evt_123)
    D-->>A: OK
    A->>D: update order pending to paid
    Note over G,A: Response lost / timeout
    G->>A: event evt_123 (retry)
    A->>D: insert ProcessedEvent(evt_123)
    D-->>A: E11000 duplicate key
    A-->>G: 200 OK (duplicate, skipped)

8. Refund Flow

Reserve amount atomically, call gateway with idempotency key, confirm via webhook. See Refund handling.md.

flowchart TD
    A[Admin requests refund: orderId, amount, reason] --> B{Order paid / partially_refunded AND refunded + amount within total?}
    B -- No --> X[Reject: not refundable]
    B -- Yes --> C[Atomically increment refundedAmount]
    C --> D[Create Refund record: requested]
    D --> E[Gateway refunds.create with idempotencyKey = refund id]
    E --> F{Gateway accepted?}
    F -- No --> G[Roll back refundedAmount, Refund = failed]
    F -- Yes --> H[Refund = pending, Order = partially_refunded / refunded]
    H --> I[Wait for webhook]
    I --> J{refund.updated / refund.processed / refund.failed}
    J -- succeeded --> K[Refund = succeeded, notify customer, restock]
    J -- failed --> L[Roll back refundedAmount, alert support]

9. How the Node App, DB and Payment Gateway Work Together

The gateway only moves money. Your Node app decides what is paid for, your DB remembers it. The link is your orderId, sent in gateway metadata and returned in every webhook. Full table in architecture.md.

flowchart LR
    UI[Client: checkout page + Stripe Elements]
    subgraph NodeApp[Node.js App]
        MW[idempotency middleware] --> RT[routes] --> CT[controllers] --> SV[payment.service]
        SV --> GWS[gateway.js: stripe SDK]
        WH[webhook route: raw body] --> SV
    end
    DB[(MongoDB: Order, Refund, ProcessedEvent)]
    RD[(Redis: idempotency keys)]
    Q[[Queue: email, invoice, stock]]
    GW[Stripe / Razorpay]

    UI -->|1. POST /orders| MW
    MW --- RD
    SV -->|2. Order pending| DB
    GWS -->|3. create PaymentIntent + orderId| GW
    SV -.->|4. client_secret| UI
    UI -->|5. pay| GW
    GW -->|6. webhook| WH
    SV -->|7. Order paid| DB
    SV -->|8. jobs| Q

sequenceDiagram
    autonumber
    participant C as Client
    participant N as Node App
    participant D as MongoDB
    participant G as Gateway

    C->>N: POST /orders (cart)
    N->>D: Read product prices (never trust client price)
    N->>D: Order {status: pending, amount: 49900}
    N->>G: create PaymentIntent (metadata.orderId)
    G-->>N: pi_123 + client_secret
    N->>D: Order {gatewayPaymentId: pi_123}
    N-->>C: client_secret
    C->>G: Pay (card / UPI / 3DS)
    G->>N: webhook payment_intent.succeeded
    N->>D: ProcessedEvent {eventId}
    N->>D: Order pending to paid
    N-->>G: 200 OK
    Note over N,D: Daily cron reconciles gateway records with DB
  1. Client sends only cart items; never the price or the secret key.
  2. Node app prices the cart from the DB and saves a pending order first, so every payment has an owner.
  3. gateway.js is the only file that imports the Stripe/Razorpay SDK; the rest of the app calls it.
  4. Webhook is what flips the order to paid, after signature, dedupe and amount checks.
  5. Queue handles email, invoice and stock so the webhook replies fast.

How to create and edit these diagrams

Every diagram above is plain text written in Mermaid syntax. The browser turns it into SVG.

  1. Add the script once (already at the bottom of this file): 
    <script src="https://cdn.jsdelivr.net/npm/mermaid@10.9.1/dist/mermaid.min.js"></script>
<script>mermaid.initialize({ startOnLoad: true });</script>
  2. Add a diagram: put Mermaid text inside a <pre class="mermaid"> block: 
    <pre class="mermaid">
flowchart TD
    A[Start] --> B{Paid?}
    B -- Yes --> C[Ship order]
    B -- No --> D[Retry payment]
</pre>
  3. Pick a diagram type for the job:
    • flowchart TD / LR: decisions and steps (verification, refund). [box], {decision}, [(database)], [[queue]].
    • sequenceDiagram: who calls whom, in order (checkout, Razorpay). ->> call, -->> reply, alt / else / end branches.
    • stateDiagram-v2: status transitions (PaymentIntent states).
  4. Avoid a literal < inside diagram text in HTML; write it as &lt; or reword it.
  5. Draft in the live editor at mermaid.live, then paste the text here.
  6. In Markdown (GitHub, VS Code preview) use a fenced block with language mermaid; architecture.md does this, so GitHub renders it directly.
